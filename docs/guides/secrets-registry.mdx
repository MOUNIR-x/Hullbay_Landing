# Secrets et registres Docker

La gestion sécurisée des credentials est essentielle dans une plateforme d'orchestration. Hullbay adopte une approche **write-only** (écriture seule) pour les secrets : vous pouvez les créer et les utiliser, mais jamais les relire en clair via l'interface ou l'API.

---

## 🔐 1. Les Secrets Docker

Les secrets Docker sont des données sensibles (mots de passe de base de données, clés API, tokens) qui sont chiffrées par le cluster Swarm (via le Raft store) et montées en fichiers dans les conteneurs. Ils ne sont jamais exposés dans les variables d'environnement en clair ni dans les labels.

### Le modèle "Write-Only"

Une fois un secret créé, **sa valeur n'est jamais retournée par l'API**, même pour un utilisateur avec le rôle `owner`. La route `GET /api/secrets` ne renvoie que les identifiants et les noms des secrets. Ce choix architectural élimine les risques de fuite accidentelle via :
- Les logs applicatifs
- Les fuites mémoire ou erreurs d'affichage
- Une éventuelle compromission de la base de données (les valeurs sont chiffrées en AES-256-GCM)

### Créer un secret

1. Accédez à la section **"Secrets"** dans le menu latéral (rôles `operator` et `owner`).
2. Cliquez sur **"Nouveau secret"**.
3. Renseignez :
   - **Nom** : Identifiant unique (ex: `DB_PASSWORD`). Caractères autorisés : `a-zA-Z0-9_.-`
   - **Valeur** : Le contenu sensible.
4. Cliquez sur **"Créer"**.

:::warning Immutabilité des Docker Secrets
Les Docker Secrets natifs sont immuables. Pour "modifier" un secret, Hullbay supprime l'ancien et en crée un nouveau. Si un service déployé référence encore ce secret, la suppression sous-jacente sera refusée par Docker, et l'API renverra une erreur `409 Conflict`. Vous devez d'abord mettre à jour le service pour qu'il n'utilise plus ce secret avant de pouvoir le supprimer.
:::

### Utiliser un secret dans un conteneur

Dans la configuration d'un nœud `container`, référencez le secret par son nom. Hullbay se charge de le monter automatiquement.

```json
{
  "image": "postgres:16-alpine",
  "secrets": ["DB_PASSWORD"],
  "environment": {
    "POSTGRES_PASSWORD_FILE": "/run/secrets/DB_PASSWORD"
  }
}
